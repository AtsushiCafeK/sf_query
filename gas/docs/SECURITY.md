# セキュリティ（GAS版）

何を守っていて、何は守れていないか。導入・運用の判断材料として、懸念も隠さず書く。

- 仕組み … [ARCHITECTURE.md](ARCHITECTURE.md)
- 構築と運用 … [OPERATIONS.md](OPERATIONS.md)

> **前提となる考え方**
> このツールは、利用者**本人の Salesforce 権限**で動く。ツール自体に強い権限はない。
> その代わり、**ツールが取れる範囲は、利用者の権限と同じ**であり、ツール側では絞れない。

---

## 1. 守っているもの

| 対象 | 守り方 |
|---|---|
| **パスワード** | 扱わない。利用者は Salesforce の画面で自分でログインする（OAuth 2.0）。SOAP のユーザー名＋パスワード方式は使わない |
| **認可コードの横取り** | PKCE（S256）。コードだけ盗まれても、`code_verifier` が無ければトークンに交換できない |
| **トークンの保管** | `PropertiesService.getUserProperties()`。**利用者ごとの領域**に保存され、他の利用者のトークンは読めない |
| **シークレット** | 持たない構成が既定（公開クライアント）。必要な場合のみスクリプトプロパティに置き、**シートには置かない** |
| **SOQLでの破壊** | SOQLは読み取り専用の言語で、更新・削除の構文がない |
| **一括登録の誤送信** | 送信前に全件検証／ドライラン／確認ダイアログ／`allOrNone`／件数上限 |
| **画面へのエラー表示** | Salesforce の応答を HTML に出すときは**エスケープ**する（`escapeHtml_`） |
| **コールバックの偽装（CSRF）** | ライブラリが `state` トークンで検証する |

## 2. 懸念（重要）

### 2-1. トークンには書き込み権限がある

**「SOQLは読み取り専用だから安全」は、SOQLの経路についてだけ正しい。**

OAuth のスコープは `api`。これは **REST API の全操作**（作成・更新・削除を含む）を、
利用者の権限の範囲で許可する。**読み取り専用のスコープは存在しない。**

つまり、トークンを使えるコードが書ければ、**その利用者の権限でデータを書き換え・削除できる**。
一括登録機能は、まさにこの権限を使っている。

- **対策**：書き込みを許したくない利用者には、Salesforce 側で**権限を与えない**（権限セット・プロファイル）。
  ツール側の設定では防げない

### 2-2. 編集者は、利用者のトークンを使うコードを書ける

スプレッドシートの**編集者は、Apps Script のコードも編集できる**。

トークンは利用者ごとに分離されているが、**コードは全員で共有**される。
悪意のある編集者がコードを書き換えると、**後でそれを実行した利用者のトークン**で、
任意の API 呼び出しや、外部への送信ができてしまう。

```
編集者A がコードを改変  →  利用者B がメニューを実行  →  B のトークンで改変コードが動く
```

- **対策**：**編集者を信頼できる少人数に限る**。「編集者＝コードを書き換えられる人」として扱う
- 閲覧のみの人には、メニューを実行させず、結果をコピーした別ファイルを渡す
- 変更履歴（Apps Script の「バージョン」・ドライブの版の履歴）で、誰がいつ変えたかを確認できるようにしておく

### 2-3. 結果シートは Salesforce の権限制御の外に出る

Salesforce では、共有ルールで「見られるデータ」が人ごとに制御されている。
しかし、**シートに書き出した時点で、そのデータはスプレッドシートの共有範囲で見られる**ようになる。

- A（広い権限）がクエリを実行し、B（権限なし）が共有されたシートを開く → **B が本来見られないデータを見られる**
- 稟議の件名・金額・申請者などは、個人情報や機微な情報を含みうる
- ダウンロード・コピー・印刷・他ファイルへの転記は、**Salesforce の監査ログに残らない**

**対策**：
- 結果シートの共有範囲を、**元データを見てよい人と同じ**にする
- 強い権限を持つ人が実行するときは、出力先の共有範囲を確認する
- 取得する項目は必要最小限にする（SOQLの `SELECT` で絞る）

### 2-4. `外部サービスへの接続` 権限

`appsscript.json` の `script.external_request` は、**任意のURLへデータを送れる**権限。
Salesforce 以外へ送る処理を混入させることもできる（2-2 の改変）。

- 権限そのものは、Salesforce の API を呼ぶために**必須**で、外せない
- **対策**：コードの改変を検知できる体制（2-2）と、コードの出所を GitHub に一本化する（OPERATIONS 6章）

### 2-5. 利用者を絞る仕組みは、Salesforce 側にある

このツールには、**「誰が使えるか」を制限する機能はない**。

- スプレッドシートを開ける人 → 共有設定で制限
- Salesforce に接続できる人 → **接続アプリのポリシー**で制限（管理者承認制＋権限セット）
- 取れるデータの範囲 → **Salesforce の権限**で制限

OPERATIONS 2-2 のとおり、接続アプリの利用者は**必ず絞る**こと。

### 2-6. シークレットを置く場合の注意

接続アプリ側が秘密を必須にしている場合に限り、スクリプトプロパティ `SALESFORCE_CLIENT_SECRET` に置く。

- **スクリプトプロパティは、編集者なら全員が読める**（コードから取得できる）
- 利用者ごとの領域（`getUserProperties`）とは別で、共有される
- シークレットが漏れた場合は、接続アプリ側で**再発行**する
- 可能なら、**秘密を必須にしない構成（PKCE のみ）**に保つ。これが最も安全

### 2-7. コンシューマー鍵（client_id）

PKCE の公開クライアント構成では、**client_id は秘密情報ではない**。
これだけでは誰もログインできない（各自の Salesforce ログインが必要）。

シートに置いて差し支えないが、気になる場合は `SALESFORCE_CLIENT_ID` をスクリプトプロパティに置けば、そちらが優先される。
ただし 2-6 のとおり、スクリプトプロパティは編集者に見える。**隠す効果は限定的**。

## 3. 一括登録に固有のリスク

読み取りと違い、**やり直しが効かない**。

| リスク | 内容 | 対策 |
|---|---|---|
| 誤登録 | 入力ミス・列のずれ・環境の取り違え | ドライラン、確認ダイアログ、**環境ごとにシートを分ける**（OPERATIONS 1章） |
| 重複登録 | 同じ行を2回実行する | 実行後、各行に**作成IDが書き戻される**。IDがある行は実行済みと分かる |
| 中途半端な登録 | 一部だけ登録される | `allOrNone: true` で全件取り消し |
| 承認フロー・通知の発火 | 登録を契機に、承認申請・メール通知・外部連携が走る | **Sandbox で確認**。取り消してもすでに飛んだ通知は戻らない |
| TeamSpirit の稟議 | 「申請」であり、APIで作ったレコードが承認フローに乗るか**未検証** | 本番では Sandbox の検証が済むまで使わない |
| 監査の弱さ | 実行履歴の専用ログはない | 作成IDの列と、Salesforce の `CreatedBy`/`CreatedDate` で追う。**実行ごとにシートのコピーを残す** |

## 4. 確認できていないこと

実際の運用で、次はまだ**検証していない**。判断の際に前提としないこと。

| 項目 | 状況 |
|---|---|
| TeamSpirit 本番での**一括登録** | 未検証。承認フロー・採番・必須の関連レコードなど |
| 旧Attachment形式の取得（Python版） | 実データ未検証 |
| 外部クライアントアプリの**ポリシー設定による利用者の絞り込み** | 画面の項目名・挙動は組織の設定で異なる。実環境で確認すること |
| 大量件数・複数人同時利用での挙動 | 未検証（GASのロックで更新は直列化されるが、負荷試験はしていない） |
| `appsscript.json` の反映状況 | 利用者の環境で反映したかは確認できない。**承認画面で権限を確認**すること |
| 退職者のトークン失効手順 | Salesforce の画面の名称は組織の設定で異なる。一度実際に試すこと |

## 5. 導入時のセキュリティチェックリスト

- [ ] 検証（Sandbox）と本番で、**スプレッドシートを分けた**
- [ ] **編集者**を信頼できる少人数に絞った（編集者＝コードを書き換えられる人）
- [ ] 接続アプリの**利用者を絞った**（管理者承認制＋権限セット）
- [ ] 利用者の **Salesforce 権限**が最小限（特に**書き込み**権限）
- [ ] 結果シートの**共有範囲**が、元データを見てよい人と同じ
- [ ] `appsscript.json` を反映し、承認画面の権限が**3つだけ**であることを確認した
- [ ] 接続アプリの「秘密が必要」が**オフ**（PKCEのみ）。やむを得ずオンなら、スクリプトプロパティで管理し、編集者に見える点を理解した
- [ ] スプレッドシートを「リンクを知っている全員」にしていない
- [ ] 異動・退職時の**トークン失効**の手順を決めた（OPERATIONS 4-3）
- [ ] 一括登録を使うなら、**誤登録時の削除手順**を Sandbox で試した
- [ ] 組織の**情報セキュリティ部門・Salesforce 管理者**に、データがスプレッドシートに出ることを共有した

## 6. 同じリポジトリの Python ツールについて

参考として、Python 版の注意点も記す（GAS版とは別の運用）。

| 点 | 内容 |
|---|---|
| 待ち受け | `127.0.0.1` のみ。**他のPCからは繋げない** |
| 画面の認証 | **画面自体にログインはない**。ポートに到達できる人は、接続中のSalesforce権限を使える |
| デバッグモード | `app.run(..., debug=True)`。Werkzeug のデバッガが有効。**ローカル専用**であることが前提 |
| 設定画面 | 認証なし。接続情報（鍵）を変更できる |
| `config.yaml` | 秘密を含みうる。`.gitignore` 済み。共有しない |

**サーバーとして社内に公開する、`0.0.0.0` で待ち受ける、といった使い方はしないこと。**
その場合は、認証・デバッグモードの無効化・HTTPS などの対応が別途必要になる。
