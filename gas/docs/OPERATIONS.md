# 本番構築と運用（GAS版）

このツールを部署に導入し、継続して運用するための手順書。
作った人以外が引き継げることを目的にしている。

- 仕組み … [ARCHITECTURE.md](ARCHITECTURE.md)
- セキュリティと懸念 … [SECURITY.md](SECURITY.md)
- 利用者向けの使い方 … [../README.md](../README.md)

## 0. 導入前の判断

導入前に、次の3点を決めておく。

| 決めること | 選択肢と目安 |
|---|---|
| **どの環境に繋ぐか** | Sandbox で試し、問題なければ本番。**最初から本番にしない** |
| **何をさせるか** | 「読み取り（SOQL実行）だけ」と「書き込み（一括登録）」はリスクが全く違う。**読み取りだけ**から始めるのが安全 |
| **誰に使わせるか** | 利用者＝そのスプレッドシートの**編集者**。編集者はコードを書き換えられる（SECURITY.md参照）。信頼できる少人数に限る |

> **一括登録は、TeamSpirit の稟議に対しては未検証。**
> 承認フローに乗るか、採番が動くかなどを Sandbox で確認するまで、本番では使わない。

## 1. 環境の分離

環境ごとに**別のスプレッドシート**を用意する。1つのシートの設定を書き換えて使い回さない。

| スプレッドシート | ログインURL | 用途 |
|---|---|---|
| `Salesforce連携_検証` | `https://test.salesforce.com`（Sandbox） | 試験・研修・新機能の確認 |
| `Salesforce連携_本番` | `https://login.salesforce.com` | 実運用 |

シート名や冒頭のセルに環境名を明記し、取り違えを防ぐ。

## 2. Salesforce 側の準備

### 2-1. 外部クライアントアプリケーション

既存のものを使うか、環境ごとに作る（本番には本番の組織で作る）。
作り方は [../../docs/04_oauth_setup.md](../../docs/04_oauth_setup.md)。

GAS版に必要な設定:

| 項目 | 値 |
|---|---|
| コールバックURL | GASのURL（下記 3-3 で取得）。複数ある場合は改行で並べる |
| OAuth範囲 | `api` と `refresh_token, offline_access` |
| 認証コードフロー | 有効 |
| Webサーバーフローの秘密が必要 | **オフ**（PKCE の公開クライアントにする） |
| 更新トークンフローの秘密が必要 | **オフ** |
| PKCE拡張を要求 | **オン** |

> 接続アプリを**編集した直後**は反映まで最大10分かかる。

### 2-2. 利用者の絞り込み（推奨）

接続アプリのポリシーで、**利用を許可する利用者を絞る**。
「全ユーザーが自分で認可できる」状態のままだと、組織の誰でもこのアプリを使えてしまう。

- 利用者を管理者承認制にし、**権限セットで許可した人だけ**にする
- 設定項目の名前は Salesforce の画面表記に従う（外部クライアントアプリケーションの「ポリシー」）

### 2-3. 利用者の Salesforce 権限

**このツールが取得・登録できる範囲は、利用者自身の Salesforce 権限そのもの。**
ツール側で絞り込む機能はない。次の点を確認する。

- 参照させたいオブジェクト・項目に、利用者が**アクセスできるか**
- **登録まで許す人**に、必要最小限の作成権限だけが付いているか
- 「全データの参照」「全データの変更」など**強い権限を持つ人**に使わせる場合は、
  その人が取れるデータがそのままシートに出る点を理解したうえで判断する

## 3. スプレッドシートと Apps Script の構築

### 3-1. 置き場所とオーナー

- スプレッドシートは**共有ドライブ**に置く。個人のドライブに置くと、
  オーナーの異動・退職でスクリプトの所有者が消え、止まる
- 個人のドライブに置く場合は、**所有者の引き継ぎ手順**を決めておく

### 3-2. コードの配置

1. スプレッドシートを作成し、**拡張機能 → Apps Script**
2. [../README.md](../README.md) の手順1の表のとおり、**6ファイルを貼り付ける**
   （`Code` `Config` `SalesforceService` `Query` `Import` `OAuth2`）
3. **`appsscript.json` を反映する**（下記）

**マニフェストの反映（権限を絞るため重要）**

Apps Script の **プロジェクトの設定 → 「appsscript.json」マニフェスト ファイルをエディタで表示する**
をオンにし、リポジトリの `gas/appsscript.json` の内容に置き換える。

反映しないと、Google が自動判定した**より広い権限**を求める場合がある
（例：スプレッドシート全体へのアクセス）。承認画面で、求められる権限が
次の3つだけであることを確認する。

| 権限 | 理由 |
|---|---|
| このスプレッドシートのみへのアクセス | 設定・結果・登録データの読み書き |
| 外部サービスへの接続 | Salesforce の API を呼ぶ |
| スプレッドシートのUI表示 | メニューとダイアログ |

### 3-3. コールバックURLの登録

1. スプレッドシートを開き直し、**Salesforce → コールバックURLを表示**
2. 表示されたURLを、2-1 の接続アプリのコールバックURLに追加
3. 反映まで最大10分待つ

> **スプレッドシートをコピーすると、スクリプトIDが変わり、コールバックURLも変わる。**
> コピーしたシートごとに、手順3-3をやり直す。やらないと `redirect_uri_mismatch` になる。

### 3-4. 設定

**Salesforce → 設定シートを作成** で「設定」シートを作り、次を入力する。

| 項目 | 本番での推奨 |
|---|---|
| ログインURL | 環境に合わせる（第1章） |
| コンシューマー鍵 | 接続アプリの値 |
| APIバージョン | `60.0` のままでよい（`60` と入れても自動で直る） |
| 最大取得件数 | 既定の5000で足りるか確認 |
| 登録先オブジェクト | 一括登録を使う場合のみ |
| 一括登録の上限件数 | **業務の実態に合わせて下げる**（月50件なら50〜60） |

### 3-5. 共有範囲

- **編集者 = コードを書き換えられる人**として扱い、最小限にする
- 閲覧のみの人に見せたい場合は、**結果シートの内容をコピーした別ファイル**を渡す
- 「リンクを知っている全員」などの公開設定にしない

### 3-6. 動作確認（初回）

1. **Salesforceに接続** → ログイン・許可
2. **接続状態を確認** → ユーザー名と組織が想定どおりか
3. 簡単な SOQL（`SELECT Id, Name FROM Account LIMIT 5` など）を実行
4. 一括登録を使う場合は、**Sandbox で必ずドライランから**

## 4. 日常の運用

### 4-1. 利用者への周知事項

- **出力した結果シートは、Salesforce の権限制御の外に出たデータ**になる。
  共有や持ち出しは、元データと同じ基準で扱う
- 一括登録は**取り消せない**。ドライランで内容を確認してから実行する
- 実行時間は約4分30秒で打ち切られる。大量に取りたいときは `WHERE` で絞る
- 「未接続」と出たら、理由の行も読む（トークン更新の失敗理由が出る）

### 4-2. 定期的な確認

| 頻度 | 確認すること |
|---|---|
| 月次 | 利用者の一覧（編集者）が妥当か。異動・退職者が残っていないか |
| 月次 | Salesforce の接続アプリの利用状況（誰が認可しているか） |
| 四半期 | `OAuth2.gs` の更新有無（出典: 公式リポジトリ）、APIバージョンの廃止予定 |
| 随時 | 設定シートの値が意図せず変わっていないか |

### 4-3. 利用者の異動・退職

1. スプレッドシートの**共有から外す**（編集権限を削除）
2. Salesforce で、その人の**接続アプリの認可を取り消す**
   （ユーザーの「接続アプリケーション OAuth 使用状況」から、または管理者が失効させる）
3. その人が作った結果シート・登録データの扱いを決める

**共有から外すだけでは不十分。** 保存済みのトークンは Salesforce 側で有効なまま残る。

### 4-4. 一括登録で誤ってデータを作ったとき

登録後は、各行の「**作成されたID**」列にレコードIDが残っている。これが唯一の手がかり。

1. 「作成されたID」列を CSV で書き出す（`Id` という見出しの1列にする）
2. 影響範囲を確認する（そのレコードから別の処理が走っていないか。承認フロー、通知、連携など）
3. 削除する。例：

   ```bash
   sf data delete bulk --sobject Ringi__c --file ids.csv --target-org <別名>
   ```

   > CLI のバージョンにより引数が異なる場合がある。**本番では必ず先に Sandbox で手順を確認する**。
   > 削除は Salesforce の画面（リストビューで選択）や、管理者に依頼する方法もある。

4. 同じ行を再登録する前に、原因（入力ミスか、設定ミスか）を直す

> **結果の書き戻しがない状態で実行・削除してはいけない。**
> 書き戻し列は消さず、実行ごとにシートのコピーを日付つきで残すとよい。

## 5. トラブルシューティング

利用者向けの一覧は [../README.md](../README.md#つまずいたときは) にある。ここでは運用者向けに補足する。

| 症状 | 原因と対処 |
|---|---|
| `redirect_uri_mismatch` | コールバックURLが未登録。**シートをコピーしていないか**確認（スクリプトIDが変わる） |
| `invalid_client` | コンシューマー鍵の不一致／接続アプリの秘密の要否の設定／反映待ち。[../README.md](../README.md#invalid_client-が出たとき) |
| 「未接続」だが接続したはず | **トークン更新に失敗している**。表示される理由の行を読む。解決しなければ「認証を解除」→「接続」 |
| `HTTP 404` | URLに `.0` が欠けていないか（`/v60/` ではなく `/v60.0/`）。最新の `Config.gs` で自動修復される |
| 実行が途中で止まる | 約4分30秒で打ち切る仕様。`WHERE` で絞る。打ち切った旨はダイアログに出る |
| 設定を変えたのに反映されない | 設定シートの項目名が変わっていないか。項目名で値を引いている |
| 数分前まで動いていたのに急に失敗 | Salesforce 側の接続アプリを編集していないか。編集直後は最大10分反映待ち |

### 一次切り分けの順序

1. エラーメッセージを**そのまま**控える（スクリーンショット）
2. **接続状態を確認** を実行する
3. Sandbox で同じ操作を試し、本番固有の問題かを見る
4. `node gas/test/test_gas.js` などは**コードの論理の確認**であり、
   Salesforce 側の設定の問題までは分からない点に注意

## 6. 変更管理

コードの正は **GitHub のリポジトリ**。Apps Script のエディタ上で直接直さない。

| 手順 | 内容 |
|---|---|
| 1 | リポジトリのコードを修正する |
| 2 | `node gas/test/test_gas.js` と `node gas/test/test_import.js` を実行する |
| 3 | **検証用**スプレッドシートに貼り替えて動作確認する |
| 4 | 問題なければ**本番用**に貼り替える |
| 5 | 変更内容を CHANGELOG に記録する |

> エディタ上で直接直すと、リポジトリと食い違い、次に貼り替えたときに修正が消える。
> 緊急で直接直した場合は、**同じ修正をリポジトリにも反映する**。

現状、貼り替えは手作業。頻繁に変更するなら、`clasp`（Google 公式のCLI）の導入を検討する。

引き継ぐ側・引き継がれる側で確認する。

- [ ] 編集者の一覧を確認し、不要な人を外した
- [ ] Salesforce の接続アプリの**管理者**と、利用者を絞る方法を把握した
- [ ] 検証用と本番用のスプレッドシートの**場所**と、それぞれのログインURLを把握した
- [ ] コールバックURLが接続アプリに**登録済み**であることを確認した
- [ ] GitHub のリポジトリへのアクセス権がある
- [ ] 一括登録を使う場合、**誤登録時の削除手順**（4-4）を一度 Sandbox で試した
- [ ] 本ドキュメントと [SECURITY.md](SECURITY.md) を通読した
